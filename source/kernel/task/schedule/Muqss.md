MuQSS - 由 Con Kolivas 开发的多队列跳表调度器

MuQSS 是原始 BFS 调度器的每 CPU 运行队列变体，每个运行队列使用一个 8 级跳表，并采用细粒度锁以实现更好的可扩展性。

目标

多队列跳表调度器（以下简称 MuQSS，发音同 mux）的目标是完全摒弃过去 CPU 进程调度器的复杂设计，转而实现一个基本设计非常简单的调度器。MuQSS 的主要焦点是在无需难以理解、无法建模和预测效果、且在为一种工作负载调优时会对另一种造成巨大损害的启发式方法和调优旋钮的情况下，实现出色的桌面交互性和响应性，同时仍能扩展到多 CPU 和多进程。

设计概要

MuQSS 最好被描述为：每 CPU 多运行队列、O(log n) 插入、O(1) 查找、最早有效虚拟截止时间优先的无滴答（tickless）设计。它松散地基于 EEVDF（最早合格虚拟截止时间优先）和我之前的 Staircase Deadline 调度器，并从单运行队列 O(n) 的 BFS 调度器演化而来。将按顺序描述每个组件以便理解其重要性和设计理由。

设计理由

在 BFS 中，跨所有 CPU 使用单个运行队列意味着每个 CPU 都需要扫描整个运行队列以寻找具有最早截止时间的进程，并调度它运行，而不管它最初来自哪个 CPU。这使得 BFS 在延迟方面是确定性的，并提供了依赖于进程数和 CPU 数的保证延迟。然而，单运行队列意味着所有 CPU 都会竞争保护它的单个锁，随着 CPU 数量的增加，这会导致锁争用增加，并且似乎限制了常见工作负载在超过 16 个逻辑 CPU 时的可扩展性。此外，运行队列链表的 O(n) 查找显然会随着排队进程数量的增加而增加开销，并在迭代链表时导致缓存抖动。

MuQSS 是 BFS 的一个演进版本，旨在通过将单运行队列拆分为每 CPU 运行队列并使用跳表代替链表，来保持相同的调度决策机制，并且几乎是确定性的，而不依赖于单运行队列的受限设计。

最初为 BFS 回归单运行队列设计的原因是，一旦引入多运行队列（每 CPU 或其他形式），就会产生复杂的交互，因为每个运行队列仅负责其自身运行队列上任务的调度延迟和公平性，而要实现跨多个 CPU 的公平性和低延迟，拥有 CPU 本地任务的任何吞吐量优势都会导致其他劣势。这是因为需要一个非常复杂的平衡系统来最好地实现跨 CPU 的某种公平性，并且只能为绑定到相同 CPU 的任务维持相对较低的延迟，而不能跨 CPU 维持。为了增加跨 CPU 的公平性和延迟，本地运行队列锁定的优势（可提供更好的可扩展性）由于必须获取多个锁而丧失。

MuQSS 通过使其跳表按优先级排序，并通过新颖地无锁检查其他每个运行队列，可以决定是否应出于延迟原因或 CPU 平衡原因从另一个运行队列中获取最早截止时间的任务，从而规避了多运行队列设计固有的问题。它仍然没有平衡系统，选择允许下一个任务调度决策和任务唤醒 CPU 选择通过其选择来实现平衡。

设计细节

自定义跳表实现：
为了避免构建和拆除跳表结构的开销，MuQSS 使用的变体进行了许多优化，使其专门适用于调度器中的用例。它使用 8 个“层级”的静态数组，而不是动态构建和拆除结构。这使得每个运行队列最多只能扩展到 O(log N) 个任务，最多 256 个任务。然而，由于每个 CPU 有一个运行队列，这意味着它可以扩展到 O(log N) 个任务，最多 256 x 逻辑 CPU 数，这远远超出了每个 CPU 可以处理的现实任务限制。通过设置为 8 级，数组的大小正好是一个缓存行。此外，每个跳表节点都是双向的，使得插入和移除的摊还成本为 O(1)，实际上是 O(k)，其中 k 为 1-8。独特的是，在 MuQSS 中，我们只对所有列表中的第一个条目感兴趣，因此永远不需要进行搜索，因此查找始终是 O(1)。

任务插入：
MuQSS 将任务作为 O(log N) 的插入操作插入到每 CPU 运行队列的自定义跳表中（基于 William Pugh 的原始设计）。插入的排序方式使得永远不需要进行搜索，主要是根据静态优先级，然后是插入时的虚拟截止时间进行排序。

Niffies：
Niffies 是一种单调向前移动的计时器，与“jiffies”类似，但具有纳秒分辨率。Niffies 是根据高分辨率 TSC 计时器为每个运行队列计算的，并且为了保持公平性，每当两个运行队列同时被锁定时，会在 CPU 之间同步。

虚拟截止时间：
在 MuQSS 中实现低延迟、调度公平性和“nice 级别”分布的关键完全在于虚拟截止时间机制。MuQSS 中的一个可调参数是 rr_interval，即“轮转间隔”。这是两个相同 nice 级别的 SCHED_OTHER（或 SCHED_NORMAL，常见的调度策略）任务将运行的最长时间，或者反过来看，两个相同 nice 级别的任务将被延迟的最长持续时间。当任务请求 CPU 时间时，它会获得一个等于 rr_interval 的时间配额（time_slice）和一个虚拟截止时间。虚拟截止时间从当前的 niffies 时间开始偏移，偏移量由以下公式计算：
niffies + (prio_ratio * rr_interval)
prio_ratio 是相对于基准 nice -20 的比率，每个 nice 级别增加 10%。截止时间只是虚拟的，因为并不保证任务实际上会在这个时间之前被调度，但它用于比较哪个任务应该下一个运行。任务被选择下一个运行有三种情况。首先是 time_slice 到期。如果一个任务用完了它的 time_slice，它会被取消调度，time_slice 会被重新填充，并且截止时间会根据上面的公式重置。其次是睡眠，即任务因任何原因不再请求 CPU。在这种情况下，time_slice 和截止时间不调整，只是在任务下次被调度时延续使用。第三是抢占，当一个新唤醒的任务被认为比任何 CPU 上当前运行的任务具有更高优先级时，这是因为它比当前运行的任务具有更早的虚拟截止时间。更早的截止时间是前两种情况中选择下一个任务的关键。

不同 nice 任务的 CPU 比例大致为：
(prio_ratio 差异)^2
之所以是平方，是因为任务的截止时间在运行时不会改变，除非它用完了 time_slice。因此，即使时间实际上已经超过了另一个排队任务的截止时间，除非当前运行的任务取消调度，否则它不会获得 CPU 时间，并且时间“基准”（niffies）在不断移动。

任务查找：
由于任务已经按照预期的调度顺序在跳表中预先排序，因此每个运行队列查找下一个合适的任务始终只是选择第 0 级跳表条目中的第一个任务。为了保持跨 CPU 的最佳延迟和公平性，MuQSS 会以一种新颖的方式按缓存局部性顺序检查所有其他运行队列，选择所有运行队列中最好的任务。这提供了接近确定性的保证，即整个系统中任何任务在接收 CPU 时间之前可能等待的时间。首先无锁地检查其他运行队列，然后尝试获取锁（trylock），以最小化它们可能拥有合适的更好任务时的潜在锁争用。每个其他运行队列锁的持有时间仅够检查条目是否合适。在“交互”模式（默认设置）下，MuQSS 将寻找所有 CPU 中具有最佳截止时间的任务，而在非交互（!interactive）模式下，仅当另一个 CPU 的负载比当前 CPU 更重时，才会从中选择具有更好截止时间的任务。
因此，查找是 O(k)，其中 k 是 CPU 数量。

延迟

通过使用虚拟截止时间来管理普通任务的调度顺序，每个运行队列的队列到激活延迟保证受限于可调参数 rr_interval（默认设置为 6ms）。这意味着一个受 CPU 限制的任务等待更多 CPU 的最长时间与运行任务的数量成正比，并且在每个 CPU 有 0-2 个运行任务的常见情况下，将低于人类感知抖动的 7ms 阈值。此外，由于新唤醒的任务将根据其先前的运行时间具有较早的截止时间，那些通常对延迟敏感的任务将具有最短的激活间隔，通常会抢占任何现有的受 CPU 限制的任务。

无滴答到期：

MuQSS 的一个特点是它不依赖于所选滴答频率 (Hz) 的分辨率，而是尽可能完全依赖高分辨率计时器来实现亚毫秒精度的超时，无论底层滴答频率如何。这允许 MuQSS 以低 Hz 频率（例如默认的 100）的低开销运行，从而受益于它提供的改进的吞吐量和更低的功耗。这种方法的另一个优点是，与完全无滴答（Full No HZ）选项（该选项在运行任务的 CPU 上禁用滴答，而不仅仅是空闲 CPU）结合，滴答可以在任何时候被禁用，无论有多少任务正在运行，而不是仅限于一个运行任务。请注意，此选项不推荐给常规桌面用户。

可扩展性与平衡

与传统方法不同，传统方法中的平衡是任务唤醒时 CPU 选择和基于大量规则（根据架构、繁忙度计算和特殊情况管理设置）的间歇性平衡的组合，而 MuQSS 在任务唤醒和下一个任务选择时间接地进行动态平衡。在初始化期间，MuQSS 为每个逻辑 CPU 创建一个缓存一致性顺序的 CPU 列表，并在 CPU 繁忙时使用此列表来辅助任务/CPU 选择。此外，它根据以下偏好随时选择任何空闲 CPU（如果可用），而不是繁忙的 CPU：

相同线程，空闲或繁忙缓存，空闲或繁忙线程

相同核心，相同缓存，空闲或繁忙缓存，空闲线程。

相同节点，其他 CPU，空闲缓存，空闲线程。

相同节点，其他 CPU，繁忙缓存，空闲线程。

相同核心，相同缓存，繁忙线程。

相同节点，其他 CPU，繁忙线程。

其他节点，其他 CPU，空闲缓存，空闲线程。

其他节点，其他 CPU，繁忙缓存，空闲线程。

其他节点，其他 CPU，繁忙线程。

因此，MuQSS 具有 SMT、多核（MC）和 NUMA 感知能力，而无需额外的间歇性平衡来维持 CPU 繁忙并充分利用缓存一致性。

特性

由于 MuQSS 最初的主要目标用户是普通桌面用户，它被设计为不需要调整、调优或设置特性即可从中受益。因此，旋钮和特性的数量已保持在绝对最低限度，并且在绝大多数情况下不需要额外的用户输入。有 3 个可选的可调参数和 2 个额外的调度策略。它们是 rr_interval、interactive 和 iso_cpu 可调参数，以及 SCHED_ISO 和 SCHED_IDLEPRIO 策略。除此之外，MuQSS 还使用亚滴答（sub-tick）统计。MuQSS 现在不具备的特性是对 CGROUPS 的支持。普通用户既不需要知道这些是什么，也不应该需要使用它们来获得良好的桌面行为。然而，由于某些应用程序没有 cgroups 就无法工作，可以在 MuQSS 中将其启用为存根（stub），文件系统将被创建，从而允许应用程序工作。

rr_interval:
/proc/sys/kernel/rr_interval
该值以毫秒为单位，默认值设置为 6。有效值从 1 到 1000。减小该值将以降低吞吐量为代价减少延迟，而增加该值将改善吞吐量，但代价是延迟恶化。这是基于人类大约在 7ms 时可以检测到抖动的事实，因此在大多数情况下，瞄准更低的延迟是没有意义的。在比较 MuQSS 与其他调度器的延迟性能时，注意到这一事实是值得的。最坏情况延迟高于 7ms 远比平均延迟不在微秒范围内要糟糕得多。

interactive:
/proc/sys/kernel/interactive
该值是一个简单的布尔值，1 表示开启，0 表示关闭，默认设置为开启。禁用此功能将禁用 MuQSS 在选择下一个任务时的近确定性，即不再检查所有 CPU 以寻找最早截止时间的任务，或唤醒到哪个 CPU，而是优先考虑 CPU 平衡以提高吞吐量。延迟仍将受 rr_interval 限制，但这是在每 CPU 的基础上，而不是跨整个系统。

等时调度（Isochronous scheduling）：
等时调度是一种独特的调度策略，旨在为非特权（即非 root）用户提供近实时性能，而不会无限期地使机器饿死。等时任务（意思是“相同时间”）可以使用，例如，schedtool 应用程序这样设置：
schedtool -I -e amarok
这将启动音频应用程序 “amarok” 为 SCHED_ISO。SCHED_ISO 的工作原理是，它具有介于真正实时任务和 SCHED_NORMAL 之间的优先级级别，允许它们以 SCHED_RR 方式（即，如果多个 SCHED_ISO 任务正在运行，它们纯粹以 rr_interval 速率轮转）抢占所有普通任务。但是，如果 ISO 任务运行超过可调的有限时间，它们会被降级回 SCHED_NORMAL 调度。这个有限的时间是每个 CPU 可用的 CPU 百分比，可在以下“资源处理”可调参数（与调度器可调参数相对）中配置为百分比：

iso_cpu:
/proc/sys/kernel/iso_cpu
默认设置为 70%。它是基于滚动 5 秒平均值计算的。因为它是总的可用 CPU，这意味着在多 CPU 机器上，一个 ISO 任务有可能仅在一个 CPU 上无限期地作为实时调度运行，因为其他 CPU 将是可用的。将其设置为 100 相当于给予所有用户 SCHED_RR 访问权限，设置为 0 则移除运行任何伪实时任务的能力。

MuQSS 的一个特性是，它会检测应用程序何时尝试获取实时策略（SCHED_RR 或 SCHED_FIFO）而调用者没有适当的权限来使用这些策略。当检测到这种情况时，它将给予任务 SCHED_ISO 策略。因此这对用户是透明的。

空闲优先级调度（Idleprio scheduling）：
空闲优先级调度是一种调度策略，旨在仅当 CPU 处于空闲状态时才将 CPU 分配给任务。这背后的想法是允许在后台运行超低优先级的任务，这些任务对前台任务几乎没有影响。这非常适用于分布式计算客户端（如 setiathome、folding、mprime 等），但也可以用于启动视频编码等，而不会减慢其他任务的速度。为了避免此策略无限期地抓取共享资源并持有它们，如果它检测到任务正在等待 I/O、机器即将挂起到 RAM 等情况，它会暂时将它们调度为 SCHED_NORMAL。一旦任务被调度为 IDLEPRIO，如果没有超级用户权限，就无法将其恢复为 SCHED_NORMAL，因为它实际上是一种更低的调度策略。可以使用 schedtool 命令将任务设置为以 SCHED_IDLEPRIO 启动，如下所示：
schedtool -D -e ./mprime

亚滴答统计（Subtick accounting）：
获得准确的 CPU 统计信息出人意料地困难，并且在许多情况下，统计只是通过确定计时器滴答触发的确切时刻发生的事情来完成的。随着计时器滴答频率 (HZ) 的降低，这变得越来越不准确。可以创建一个使用几乎 100% CPU 的应用程序，通过在正确的时间被取消调度，记录为零 CPU 使用率。虽然这个问题的主要是可能存在安全隐患，但也很难确定一个任务实际使用了多少 CPU。MuQSS 使用来自 TSC 时钟的亚滴答统计来确定真实的 CPU 使用情况。因此，MuQSS 报告使用的 CPU 量将更准确地表示任务本身正在使用的 CPU 量（例如，由 'time' 应用程序显示的那样），因此报告的值可能与其他调度器有很大不同。在比较 MuQSS 与其他设计的吞吐量时，重要的是根据完成的总工作所花费的总挂钟时间和完成的总工作量进行比较，而不是比较报告的“CPU 使用率”。

对称多线程（SMT）感知的 nice：
SMT，又名超线程，是现代 CPU 上非常常见的功能。虽然逻辑 CPU 数量通过向每个 CPU 核心添加线程单元而增加，允许在同一核心上同时运行多个任务，但其缺点是 CPU 功率在任务之间共享，而不是汇总到两个 CPU 的功率。这样做的实际结果是，在两个相同核心的不同线程上运行的两个任务比它们各自拥有一个核心运行要慢得多。虽然智能 CPU 选择允许每个任务在可用时拥有一个核心（如在 MuQSS 上所做的那样），但它不能抵消在所有核心都已加载且只剩下线程时发生的减速。大多数情况下这是无害的，因为此时 CPU 实际上已过载，额外的线程是有益的。然而，当在存在非 niced 任务（例如 nice 19 与 nice 0）的情况下运行 niced 任务时，niced 任务获得的 CPU 功率与非 niced 任务完全相同。MuQSS 有一个可选的配置特性，称为 SMT-NICE，它选择性地使次要的 niced 线程空闲一段时间，该时间与 nice 差异成正比，从而允许根据 nice 级别维持 CPU 分配，但代价是少量的额外开销。如果在没有 SMT 线程的机器上配置此功能，开销是最小的。

"prio_ratio 是相对于基准 nice -20 的比率" 那么对于nice=-20的情况下, MuQss的prio_ratio为多少?
在 MuQSS 中，prio_ratio 的计算是基于一个基准（nice -20），并且每个更高的 nice 级别（即更低的优先级，数值更大）会增加 10%。

对于基准 nice 级别 -20，其 prio_ratio 被定义为 1.0（或 100%）。

这意味着：

nice -20 的任务：prio_ratio = 1.0

nice -19 的任务：prio_ratio = 1.0 * 1.1 = 1.1

nice -18 的任务：prio_ratio = 1.1 * 1.1 = 1.21

...

nice 0 的任务：prio_ratio = 1.0 * (1.1)^20 ≈ 6.7275

nice 19 的任务：prio_ratio = 1.0 * (1.1)^39 ≈ 41.1445

因此，一个 nice -20 的任务的虚拟截止时间计算为：
niffies + (1.0 * rr_interval)

这给了它最短的时间偏移量，从而在所有 SCHED_NORMAL 任务中具有最早的虚拟截止时间和最高的优先级。

等时任务(iso)是什么
好的，这是一个关于 MuQSS 调度器中等时任务（Isochronous Task） 的详细解释。

核心概念
等时任务（由 SCHED_ISO 策略调度）是 MuQSS 引入的一种类实时任务。它的设计目标是：为普通（非 root）用户提供接近实时的性能，但同时防止这些用户因误用或滥用而完全“饿死”系统（即让其他所有任务都无法获得 CPU 时间）。

您可以把它理解为一个位于普通任务（SCHED_NORMAL）和真正的实时任务（SCHED_FIFO, SCHED_RR）之间的安全中间层。

工作原理
高优先级：SCHED_ISO 任务的优先级高于所有 SCHED_NORMAL 任务。这意味着当一个等时任务准备就绪时，它可以立即抢占任何正在运行的普通任务。这对于需要低延迟和稳定周期的应用程序（如音频播放、视频录制、实时通信）至关重要，可以防止音频出现爆裂声或视频卡顿。

轮转调度：如果有多个 SCHED_ISO 任务同时运行，它们之间会以轮转（Round-Robin） 的方式共享 CPU。每个任务最多运行一个 rr_interval（默认 6ms）的时间片，然后切换到队列中的下一个等时任务。这确保了多个等时任务之间的公平性。

安全限制（防饿死机制）：这是 SCHED_ISO 最关键的特性。它不是一个“无限”的实时策略。系统会监控所有 SCHED_ISO 任务在所有 CPU 上的总 CPU 使用率（基于一个滚动的 5 秒平均窗口）。

有一个可调参数 iso_cpu（默认设置为 70%），它定义了允许 SCHED_ISO 任务使用的系统总 CPU 能力的最大百分比。

只要所有 SCHED_ISO 任务的总使用率低于这个阈值，它们就能享受其高优先级。

一旦它们的总使用率超过 iso_cpu 阈值，超出的单个 SCHED_ISO 任务会被自动降级**为普通的 SCHED_NORMAL 任务，直到其使用率回落为止。这可以防止一个失控的等时任务或过多的等时任务拖垮整个系统。

举例说明
音频播放器 (amarok)：这是最经典的用例。你使用命令 schedtool -I -e amarok 启动它。播放器线程被设置为 SCHED_ISO。这意味着当声卡需要新的音频数据时，播放器线程几乎可以立即被调度，从而提供流畅的播放体验，即使系统正承受编译代码等重负载。同时，由于限制的存在，即使用户让多个音频播放器以 SCHED_ISO 运行，它们最多也只能占用 70% 的总 CPU，剩下的 30% 仍然可供系统和其他普通任务使用，保证了系统的整体响应能力。

视频会议软件：为了保证视频和音频流的实时编码和传输，避免卡顿，可以将其设置为 SCHED_ISO。

MuQSS 还有一个贴心功能：如果一个没有 root 权限的应用程序错误地尝试将自己设置为 SCHED_FIFO 或 SCHED_RR，MuQSS 不会直接拒绝请求导致程序出错，而是会透明地将其降级为 SCHED_ISO 策略。这样既保证了系统的安全，又允许程序继续运行。

总结
等时任务（SCHED_ISO）是 MuQSS 调度器的一项创新功能，它巧妙地平衡了低延迟需求和系统稳定性。它让普通桌面用户也能享受到实时调度带来的好处（如出色的音频、视频体验），而无需承担因拥有完全实时权限而可能带来的系统崩溃风险。它是一个“安全的实时模式”。

等时任务不需要参考虚拟截止时间(virtual deadline)进行排序吗
这是一个非常棒的问题，它触及了 MuQSS 设计中的一个精妙之处。

简短的回答是：不，等时任务（SCHED_ISO）不参与基于虚拟截止时间（Virtual Deadline）的排序。 它们使用一套完全独立且更简单的机制。

详细解释如下：

MuQSS 的核心调度队列机制是基于虚拟截止时间的，但这主要针对的是 SCHED_NORMAL（普通）任务。SCHED_ISO 和 SCHED_RR/SCHED_FIFO 这些实时策略的任务有各自的处理方式。

1. 优先级层级
首先，要理解 MuQSS 中的优先级层次结构是严格的：

SCHED_FIFO / SCHED_RR > SCHED_ISO > SCHED_NORMAL > SCHED_IDLEPRIO / SCHED_BATCH

这意味着：

只要有任何一个实时任务（FIFO/RR）可运行，它就会抢占任何 ISO 或 NORMAL 任务。

只要有任何一个等时任务（ISO）可运行，它就会抢占任何 NORMAL 任务。

调度器只有在高优先级队列为空时，才会去检查低优先级队列。

2. 等时任务（SCHED_ISO）的调度机制
由于 SCHED_ISO 任务处于一个独立的、更高优先级的层级，它们完全绕过了为 SCHED_NORMAL 任务设计的虚拟截止时间排序系统。它们有自己的运行队列和调度规则：

独立的队列：每个 CPU 的运行队列中都有一个专门用于存放 SCHED_ISO 任务的列表。

简单的轮转（Round-Robin）：SCHED_ISO 任务之间的调度不计算截止时间。它们的规则非常简单：

当一个 SCHED_ISO 任务被唤醒或产生时，它被加入到当前 CPU 的 ISO 队列中。
调度器在选择下一个任务时，如果发现 ISO 队列非空，就会从这个队列中选取第一个任务来运行。
该任务被授予一个固定的时间片（就是 rr_interval，例如 6ms）。
当它用尽时间片后，它会被放回其 ISO 队列的末尾。
然后，调度器选择同一个 ISO 队列中的下一个任务（即队首的任务）运行。
这个过程循环往复，实现了纯粹的、公平的轮转调度。
所以，对于 SCHED_ISO 任务，排序的依据是它们进入队列的“先进先出”顺序，而不是虚拟截止时间。

3. 虚拟截止时间机制的角色
虚拟截止时间机制只适用于 SCHED_NORMAL 任务。它的作用是：

在大量的普通任务中决定谁更“紧急”。

实现 nice 值之间的公平CPU时间分配。

提供低延迟的调度保证。

当一个 SCHED_ISO 任务被唤醒时，它根本不需要和 SCHED_NORMAL 任务比较截止时间，因为它天生就具有更高的优先级类别，可以直接抢占。同样，两个 SCHED_ISO 任务之间也不需要比较，因为它们遵循简单的轮转规则。

总结对比
特性	SCHED_NORMAL 任务	SCHED_ISO 任务
排序机制	基于虚拟截止时间 (Earliest Eligible Virtual Deadline First)	基于队列位置 (简单的 Round-Robin/FIFO)
优先级决定	由 nice 值通过公式换算成虚拟截止时间	由策略本身决定（高于NORMAL，低于RR/FIFO）
时间片	动态的 time_slice，但初始值等于 rr_interval	固定的 rr_interval
目标	公平性、低延迟、响应性	低延迟抢占，同时防止系统饿死
因此，你的问题的答案非常明确：等时任务不参考虚拟截止时间进行排序。 虚拟截止时间是 MuQSS 用于管理普通任务庞大队伍的复杂而公平的算法，而等时任务作为拥有“特权”的VIP，走的是完全不同的快速通道。

SCHED_NORMAL 任务 的time_slice是如何动态计算的
非常好的问题。在 MuQSS 中，SCHED_NORMAL 任务的 time_slice 动态计算机制是其设计的核心之一，它与传统的 CFS 或 O(1) 调度器有根本性的不同。

MuQSS 中的 time_slice 不是一个根据优先级或权重静态计算的固定值，而是一个动态消耗和补充的配额。其动态性体现在运行时的消耗和特定条件下的重置。

以下是其动态计算和工作原理的详细说明：

1. 初始分配 (Initial Allocation)
当一个任务被创建、被唤醒（从睡眠中），或者耗尽其当前 time_slice 时，它会获得一个新的 time_slice 配额。这个初始值直接由可调参数 rr_interval 决定。

初始值公式：
time_slice = rr_interval

例如，如果 rr_interval 是默认的 6 毫秒，那么任务每次被“补充”时，都会获得 6 毫秒的 CPU 时间配额。

2. 运行时消耗 (Runtime Consumption)
任务在 CPU 上运行时，会持续地消耗它的 time_slice。关键点是：

消耗的精度非常高：得益于亚滴答记账（Subtick Accounting），MuQSS 使用高精度的 TSC 寄存器来测量任务实际使用的 CPU 时间，而不是依赖于低精度的定时器滴答（HZ）。这意味着即使任务只运行了非常短的时间（例如几微秒），它的 time_slice 也会被精确地扣除相应的量。

3. 重置条件 (Reset Conditions)
time_slice 在以下两种主要情况下会被重置为 rr_interval：

a) 主动用完 (Expiration)

这是最主要的情况。如果一个任务持续运行，直到其 time_slice 被消耗至 0，它会被强制从 CPU 上撤下（descheduled）。

在它被重新放回运行队列之前，它的 time_slice 会被重置为 rr_interval。

同时，它的虚拟截止时间（Virtual Deadline）也会被重新计算（niffies + (prio_ratio * rr_interval)），然后它被插入到跳表中的新位置。

b) 外部唤醒 (Wakeup)

当一个任务主动放弃 CPU（例如进行 I/O 操作、等待锁、调用 sched_yield() 或 sleep()）时，它进入睡眠状态。

重要：在这种情况下，它的 time_slice 不会被重置。当前剩余的 time_slice 和之前计算的虚拟截止时间会被保留。

当该任务后来被唤醒时，它会带着之前剩余的 time_slice 和旧的、但可能仍然很早的虚拟截止时间重新加入运行队列。

这个机制对交互式任务极其有利：一个经常睡眠的交互式任务（如文本编辑器、终端），每次被唤醒时都可能还剩下很多 time_slice，并且其截止时间是在很久以前计算的（niffies 是当前时间，而它的截止时间是基于过去的某个时间计算的），因此它的虚拟截止时间会非常早，从而拥有非常高的优先级，能够快速抢占正在运行的 CPU 消耗型任务。

动态性总结
MuQSS 中 time_slice 的“动态”一词，指的是它的状态（剩余量）是动态变化的，而不是指它的初始值是动态计算的。

行为	对 time_slice 的影响	对虚拟截止时间的影响
任务运行	持续减少（精确扣除）	不变
时间片用完	重置为 rr_interval	重新计算（新的未来时间）
任务睡眠	保留剩余值	保留旧值（变得更具竞争力）
任务被唤醒	保持睡眠前剩余值	保持睡眠前的旧值
与传统调度器的对比
CFS：CFS 没有 time_slice 的概念。它通过虚拟运行时（vruntime） 来跟踪任务的进度，目标是使所有任务的 vruntime 相等。调度决策基于最小的 vruntime。

O(1)：O(1) 调度器有静态的、基于优先级的 time_slice。高优先级任务获得更长的固定时间片，低优先级任务获得更短的固定时间片。消耗完后统一重置。

MuQSS：time_slice 是一个统一的初始配额（所有 SCHED_NORMAL 任务一开始都是 rr_interval），其动态性体现在运行中消耗和用完后重置。任务的优先级不通过 time_slice 的长度来体现，而是通过虚拟截止时间公式中的 prio_ratio 来体现。一个高优先级（低 nice值）的任务会有更小的 prio_ratio，因此其截止时间更近，更容易被调度，但它每次获得的 time_slice 配额和低优先级任务是一样的。

这种设计使得 MuQSS 的实现非常简单，同时又能有效地区分任务优先级（通过截止时间）并为交互式任务提供优异的响应性（通过保留睡眠任务的剩余时间和早期截止时间）。

条件类型	说明
虚拟截止时间更早	新任务或被唤醒任务的虚拟截止时间比某个CPU上当前运行任务的虚拟截止时间更早

🔍 抢占的具体条件
在MuQSS中，一个任务（无论是新创建还是从睡眠中唤醒）被插入到某个CPU的运行队列后，调度器会检查是否需要在其他CPU上抢占当前正在运行的任务。抢占的发生基于以下核心机制：

虚拟截止时间比较：MuQSS调度策略的关键是最早合格虚拟截止时间优先（EEVDF） 的变体。每个任务都有一个虚拟截止时间（virtual deadline），计算方式为：niffies + (prio_ratio * rr_interval)。其中prio_ratio与任务的nice值相关（nice值越低，prio_ratio越小，虚拟截止时间越早）。调度器会选择虚拟截止时间最早的任务来运行。如果一个新插入或刚唤醒的任务的虚拟截止时间早于某个CPU上当前正运行任务的虚拟截止时间，就可能发生抢占。

全局搜索与交互模式：默认情况下，MuQSS处于交互模式（interactive mode）。在此模式下，当需要决定下一个运行的任务时，每个CPU都会尝试检查所有其他CPU的运行队列（以缓存局部性顺序），寻找所有就绪任务中虚拟截止时间最早的那个任务，而不仅仅是本地运行队列中的任务。如果发现某个CPU上的当前运行任务的截止时间晚于这个新发现的“最早截止时间任务”，并且这个最早截止时间任务不在当前CPU上，那么就会发生跨CPU抢占：那个截止时间更早的任务将抢占截止时间较晚的任务所在的CPU。

非交互模式的行为：如果关闭了交互模式（interactive设置为0），MuQSS则不会总是寻找所有CPU中最早截止时间的任务。此时，它仅当另一个CPU的运行队列负载明显更重（more heavily laden）时，才会考虑从那个CPU抢占当前任务，以进行负载均衡，更侧重于吞吐量而非全局最低延迟。

CPU选择与任务唤醒：当一个任务被唤醒时，调度器需要决定在哪个CPU上运行它。MuQSS会尝试选择最合适的CPU：

优先选择空闲CPU。

若无空闲CPU，则根据缓存亲和性、NUMA结构等因素选择一个CPU，目的是减少缓存失效和内存访问延迟带来的性能开销。

一旦目标CPU确定，就会将任务加入该CPU的运行队列。随后，如果该任务的虚拟截止时间早于目标CPU上当前运行任务的虚拟截止时间，就会抢占该CPU。

⚠️ 需要注意的几点
“优先级”的实质：在MuQSS中，决定调度顺序的首要因素是虚拟截止时间，而非传统的静态优先级。虽然任务的nice值会影响虚拟截止时间的计算（从而影响其“优先级”），但一个刚唤醒的交互式任务可能因为保留了之前的早期截止时间，其虚拟截止时间可能比一个正在运行的CPU消耗型任务更早，即使后者的静态nice值更优。这是MuQSS保证交互性能的关键。

锁与效率：MuQSS在检查其他运行队列时，会先进行无锁（lockless）检查，仅当发现可能存在更好的候选任务时，才会尝试获取该运行队列的锁（trylock），以最小化锁竞争带来的开销。

与实时进程的区别：以上讨论主要针对普通进程（SCHED_NORMAL） 和等时进程（SCHED_ISO）。对于真正的实时进程（SCHED_FIFO, SCHED_RR），它们具有最高的静态优先级，一旦就绪，就可以抢占任何非实时进程。MuQSS的行为也需要遵循这个基本原则。

💎 结论
所以，在MuQSS中，一个任务插入后，并非简单比较它与所有CPU上运行任务的静态优先级来决定抢占。而是主要看它的虚拟截止时间是否早于某个CPU上当前运行任务的虚拟截止时间，并且调度器会在所有CPU中寻找最早截止时间的任务来调度（默认交互模式下）。因此，抢占可以发生在任何一个其当前运行任务虚拟截止时间晚于新发现的全局最早截止时间任务的CPU上，以此保证系统的响应性和公平性。

在 MuQSS（Multiple Queue Skiplist Scheduler）调度器中，任务的插入是一个关键操作，它直接影响到调度器的效率和性能。MuQSS 使用每CPU跳表（per-CPU skiplist） 来管理任务队列，任务的插入过程主要涉及确定插入位置和维护跳表结构。

下面我用一个表格来汇总 MuQSS 中任务插入的主要特点，以便你快速了解：

特性	说明
数据结构	每CPU跳表（8层）
插入复杂度	O(log N)
排序依据	1. 静态优先级（static priority）
2. 虚拟截止时间（virtual deadline）
关键机制	跳表插入、虚拟截止时间计算
优势	插入高效、有序性、适用于桌面交互环境
🔍 任务插入的基本步骤
当一个任务需要被插入到某个CPU的运行队列中时，MuQSS 会执行以下步骤：

选择目标运行队列：MuQSS 是每CPU运行队列（per-CPU runqueue） 的设计。因此，任务会根据其CPU亲和性（affinity）、调度策略以及系统的负载情况，被选择插入到某一个特定CPU的运行队列中。这避免了单一队列带来的锁竞争问题。

计算虚拟截止时间：对于 SCHED_NORMAL（普通）任务，MuQSS 使用虚拟截止时间（Virtual Deadline） 来决定任务的调度顺序。虚拟截止时间的计算公式通常为：
virtual_deadline = niffies + (prio_ratio * rr_interval)。

niffies：一个纳秒级的单调递增计时器，类似于 jiffies，但精度更高。

prio_ratio：与任务的静态优先级（或nice值）相关的比率。优先级越高（nice值越低）的任务，其 prio_ratio 越小，计算得到的虚拟截止时间也就越早（值越小），从而获得更高的调度优先级。

rr_interval：一个可调参数，表示轮转时间间隔，默认约为6ms。
对于实时任务（如 SCHED_FIFO, SCHED_RR）或等时任务（SCHED_ISO），其调度优先级由不同的策略决定，不依赖于虚拟截止时间。

按序插入跳表：任务会按照静态优先级和虚拟截止时间被插入到对应CPU运行队列的跳表中。跳表（Skiplist）是一种可以快速查找、插入和删除的数据结构，它通过维护多级索引来达到接近平衡树的效率，但实现起来更简单。

插入操作的时间复杂度为 O(log N)，其中 N 是队列中的任务数。这是因为跳表允许算法在各级索引中快速定位插入点。

任务在跳表中大致按虚拟截止时间排序，但静态优先级是首要考虑因素。这意味着高优先级的任务即使虚拟截止时间稍晚，也可能会排在低优先级但虚拟截止时间稍早的任务之前。

⚙️ 插入过程中的关键机制
跳表的作用：MuQSS 为每个CPU的运行队列使用一个自定义的跳表（通常有8层）。这种跳表使用静态数组而非动态分配节点，以减少构建和销毁结构的开销。跳表的结构使得查找下一个要运行的任务（即跳表首位的任务）的时间复杂度为 O(1)，这对于调度器的快速决策至关重要。

niffies 的作用：niffies 是一个高精度、每CPU的计时器，用于计算任务的虚拟截止时间，确保调度的精确性和公平性。

与BFS调度器的区别：MuQSS 的前身 BFS（Brain Fuck Scheduler）使用一个全局的双向链表来管理所有任务，任务插入时简单地放到链表尾部，选择任务时需要遍历整个链表（O(N)复杂度）。MuQSS 通过改为 per-CPU 跳表并将插入复杂度降至 O(log N)，显著提升了可扩展性和效率。

🌟 总结
MuQSS 中的任务插入是一个经过精心设计的过程，它通过每CPU跳表和基于虚拟截止时间与静态优先级的排序，在保证调度公平性和响应性的同时，提升了多核环境下的性能。其 O(log N) 的插入复杂度 和 O(1) 的查找下一个任务的能力，使得 MuQSS 特别适合桌面交互环境，能够为用户提供流畅的体验。

1. 确定排序键
对于普通任务（SCHED_NORMAL）：

调度器会为任务计算一个虚拟截止时间。

计算公式：Virtual Deadline = niffies + (prio_ratio * rr_interval)

niffies：一个高精度的纳秒级计时器。

prio_ratio：由任务的 nice 值决定。nice 值越低（优先级越高），该比率越小，计算出的截止时间就越早。

rr_interval：轮转间隔，是可调参数（默认~6ms）。

这个虚拟截止时间就是任务在队列中的 “排序键”。

对于实时任务（SCHED_ISO/FIFO/RR）：

它们不计算虚拟截止时间。

它们拥有绝对的优先级，会被放入专门的实时任务队列，普通任务的调度与此队列无关。

2. 选择目标运行队列 & 插入
MuQSS 是每 CPU 运行队列设计，因此需要先确定将这个任务插入到哪个 CPU 的队列中。选择策略会考虑：

CPU 亲和性

缓存局部性（优先选择上次运行的 CPU）

负载情况（优先选择空闲 CPU）

任务被加入到目标 CPU 的运行队列中，该队列是一个自定义的 8 级跳表。

插入排序规则：

首要依据是任务的静态优先级。
在静态优先级相同的情况下，再根据虚拟截止时间排序，截止时间越早（值越小）的任务位置越靠前。
3. 触发抢占检查
插入完成后，调度器会进行一次全局的抢占检查。

它会无锁地快速扫描所有 CPU 上当前正在运行的任务的虚拟截止时间。

如果发现新插入任务的虚拟截止时间 比 某个 CPU 上正在运行的任务的虚拟截止时间 更早，则调度器会尝试抢占那个 CPU，让其切换到更早截止时间的任务（可能就是刚插入的这个任务）。

这个机制确保了整个系统中虚拟截止时间最早的任务能尽快得到运行，从而保证低延迟。

核心特点总结
高效插入：得益于跳表数据结构，插入操作的复杂度为 O(log N)，这在任务数量较多时依然能保持高效。

全局最优：通过插入后的全局抢占检查，MuQSS 实现了近似的全局最早截止时间优先调度，而不仅仅是单个 CPU 队列内的最优。

兼顾优先级与公平：通过静态优先级和虚拟截止时间的结合，既保证了高优先级任务能得到优待，又能在同优先级任务间实现公平的进度推进。

这个插入过程是 MuQSS 能够实现其低延迟和高响应性目标的关键所在。

MuQss内部调度过程是怎么使用try_lock的

在 MuQSS 调度器中，try_lock 机制主要用于在检查其他 CPU 运行队列时尝试获取其锁，目的是为了最小化多运行队列扫描带来的锁竞争开销，并在此基础上确定是否需要进行任务抢占或负载均衡。下面这个表格概括了其主要使用场景和特点：

使用场景	目的	操作方式
全局任务查找	寻找所有CPU上具有最早虚拟截止时间的任务	先无锁检查其他运行队列，若可能有更好的任务，再尝试 try_lock
减少锁竞争	避免在扫描多个运行队列时因直接阻塞加锁导致的性能下降	使用 try_lock 非阻塞地尝试获取锁，失败则跳过该队列
交互模式决策	在不同模式下（默认交互模式或非交互模式）决定是否跨CPU抢占	交互模式下，try_lock 成功后会比较虚拟截止时间，决定是否抢占
🔍 工作流程简述
MuQSS 在需要寻找下一个要运行的任务时（例如，当前任务用完时间片或被唤醒），其调度过程可以简要概括为：

选择候选任务：首先，调度器会从当前CPU的运行队列中选取当前虚拟截止时间最早的任务（位于跳表最前面）作为候选。

扫描其他运行队列：接着，调度器会按照缓存亲和性顺序扫描其他CPU的运行队列。

无锁初步检查：在尝试获取其他运行队列的锁之前，调度器会先进行无锁（lockless）的初步检查。这主要是为了快速查看其他队列中是否可能存在比当前候选任务虚拟截止时间更早的任务。如果初步判断没有，则跳过该队列，避免不必要的锁操作。

尝试加锁（try_lock）：如果无锁检查认为某个其他运行队列中可能包含更好的任务，调度器就会尝试使用 try_lock 来获取该运行队列的锁。

如果 try_lock 成功（获取了锁），调度器就可以安全地访问该队列，取出其队首任务，比较其虚拟截止时间与当前候选任务。如果发现该任务的虚拟截止时间更早，则将其作为新的候选任务，并记录其所在的CPU。最后，释放该队列的锁。

如果 try_lock 失败（该运行队列的锁已被其他CPU持有），调度器则不会等待，而是直接跳过此队列，继续检查下一个。

最终调度决策：在扫描完所有其他运行队列（或达到某种条件）后：

如果在其他CPU的运行队列上找到了虚拟截止时间更早的任务，并且系统处于交互模式（默认），则可能触发跨CPU抢占，将该任务迁移到当前CPU运行，或唤醒空闲CPU来运行它。

如果系统处于非交互模式，则通常只在目标CPU比当前CPU"更繁忙"时，才考虑从那里取任务。

💎 核心作用
MuQSS 中 try_lock 的使用，核心是在保证调度质量（找到尽可能早的任务）和降低锁开销之间取得平衡。它避免了在全局查找最佳任务时，因盲目等待所有运行队列的锁而引入的潜在性能瓶颈和稳定性问题，这对于提升多核系统下的调度器效率和响应速度至关重要。
